# 制作、应用交接与交付

## 按项目选工具

| 阶段 | 需要解决的问题 | 交接物 |
|---|---|---|
| 素材制作 | 实拍、录屏、图像或生成片段如何获得 | 媒体文件、来源与授权 |
| 画面与动画 | 构图、文字、图表、动效如何实现 | 场景源文件或导出片段 |
| 剪辑合成 | 如何安排音轨、场景、字幕与转场 | 时间轴与剪辑工程 |
| 输出 | 播放平台及后续编辑需要什么 | 视频、字幕和约定的源文件 |

用户指定应用时围绕它工作；现有工程优先沿用。未指定时按任务需求和已具备能力选择，不强制单个应用包办全流程。例如代码动画、传统剪辑或生成视频都可成为某一阶段，但不因名称出现就假定已具备集成能力。

在 `PRODUCTION.md` 记录所选工具、实际版本、阶段输入输出、可执行操作与手工步骤。新增应用的经验可沉淀在 `references/adapters/`；只有真实运行验证后才标为已验证。

## 通用交接约定

- 分镜 Frame 是叙事场景编号，不是编码视频帧。场景源可为素材文件、应用工程内的序列名、动画工程或代码文件。
- 音频索引 `start`、`audio_duration`、`duration` 单位为秒；路径相对项目根目录。导入应用时确认帧率和时间基准，避免逐段四舍五入累积误差。
- 内置音频索引是顺序拼接独立口播段的时间计划，尚未生成拼接母带；留白需在目标应用时间轴上实际安排。
- 素材转码或跨应用导出时，记录分辨率、帧率、色彩、透明度、音频采样率及编码参数，检查是否损失必要信息。
- 长片按章节制作并验证。先导出短样或草片，再检查整片；资源限制和失败恢复方法按应用选择，不通用强制 streaming。

## 完成条件

验证媒体可读取、无缺失字体或素材、场景和旁白对齐，检查章节边界、文字数据、字幕、音量和目标平台参数。应用有原生检查工具时使用，再结合实际播放和抽帧检查。

交付时说明输出文件、可编辑工程、使用的应用、已完成的验证及仍需手工完成的部分。用户只要求素材或草稿时，以该阶段产物为完成条件。

用户要求上传或发布成片时，继续阅读 [平台发布](publishing.md)，默认通过 Edge 操作创作者网页，先检查工具连接与登录，再按目标平台及授权执行。发布结果与成片交付分别记录。

目前内置的应用专属模板为 [HyperFrames](adapters/hyperframes.md)；其他应用通过通用文档、素材和音频索引交接，尚无内置自动转换器。

## 少即是好，但「少」不等于「只有字」

用户对一个全部达标的成片只提了两个要求：「没有字幕」和「视频怎么都是黑白的」。两句话都指向同一点：**交付前确认「作品实际长什么样」，而不是「流程是否跑通」。**

门禁全过、check 0 错误、渲染成功、时长准确 —— 技术上没问题，但用户看到的可能是一面墙的字和一片黑白。**门禁检查不了「画面是否在承载信息」**，只能靠看。

## 保留清晰度上限：用 preview 迭代，render 只跑一次

1007s / 67 帧渲染一次 14 分钟。为省时间不要「改一点渲一次」：

```
preview（常驻，改文件自动重载）→ 看 → 改 → 再看 → 满意后render 一次
```

先给用户看**粗剪版完整成片**（模板批量生成，不精修），拿到可播放的完整片子和正确时间轴，再决定哪些帧值得精修。反过来先精修 67 帧、结果方向错了，返工量高得多。

## 交付前自查三个「只能靠看发现」的问题

技术检查抓不到这三个，必须实际看画面：

1. **画面在承载信息吗** —— 逐帧问「去掉文字后还剩什么」。空的就��文字墙。详见 [分镜与脚本](storyboard.md)
2. **颜色被压掉了吗** —— 为「统一色调」给素材加了 `grayscale(1)`，结果全片黑白。正确做法是 `saturate(0.5~0.6)` 降饱和保色相，详见 [HyperFrames 适配](adapters/hyperframes.md)
3. **用户看的是你以为的那个东西吗** —— 遗留文件、缓存、旧工程文件都会让用户看到的与实际渲染的不是一个东西。删旧文件、`curl` 服务端确认返回的是新内容、再要求硬刷新
